# 클로드 활용 구현 작업 가이드

## 원칙

하나의 대화에서 하나의 모듈만 다룬다.
각 모듈은 "설계 검증 → 구현 → 테스트"의 3단계를 거친다.
앞 모듈의 출력 스키마가 뒷 모듈의 입력이 되므로, 스키마를 먼저 확정한다.

---

## 대화 시작 시 항상 제공할 것

매 대화의 첫 메시지에 아래 3가지를 함께 붙여넣는다:

1. **PROJECT_GUIDELINES.md** (전체 지침 - 프로젝트 문서에 등록)
2. **현재 작업 대상** (아래 작업 목록에서 해당 항목)
3. **이전 단계 산출물** (이전에 확정된 스키마, 인터페이스, 코드 파일)

---

## 작업 목록 및 주문 템플릿

### STEP 0: 데이터 스키마 확정

이 단계가 전체 프로젝트의 기반이다. 여기서 확정된 스키마가 이후 모든 모듈의 입출력 계약이 된다.

```
[주문 예시]

PROJECT_GUIDELINES.md를 참고해서 아래 작업을 수행해줘.

작업: 전체 프로젝트의 데이터 스키마 설계

아래 4가지 스키마를 Python dataclass 또는 Pydantic 모델로 정의해줘:

1. 센서 Raw 데이터 모델
   - 제안서 15페이지의 JSON 구조 기반
   - 센서 종류별(온도/습도/조도/활동량/활동감지/화재/응급호출/출입) 각각 정의
   - 모바일앱 데이터(위험도 판단 결과, GPS) 포함

2. Edge AI 전처리 결과 모델
   - Kalman Filter → EWMA → IF 파이프라인의 중간/최종 출력
   - 상황등급(관심/주의/위험) 포함

3. Edge → Core 전달용 축약 데이터 모델
   - Core AI가 받아서 추론에 사용할 수 있는 포맷

4. Core AI 판단 결과 모델
   - 추론 결과, 위험도, 예측 등급, 근거 데이터 참조

각 모델 간의 변환 관계도 명시해줘.
구현 전에 먼저 설계안을 제시하고, 내가 확인한 뒤 코드로 작성해.
```

**검증 포인트**:
- 센서 JSON 예시와 1:1 매핑되는지 확인
- 모델 간 변환 시 누락 필드가 없는지 확인
- 타임스탬프 형식, 단위가 통일되었는지 확인
- 이후 모듈에서 필요한 필드가 빠지지 않았는지 지침서와 대조

### STEP 1: Expert System (규칙 엔진)

```
[주문 예시]

PROJECT_GUIDELINES.md와 첨부한 schemas.py를 참고해서 아래 작업을 수행해줘.

작업: Edge AI - Expert System 규칙 엔진 구현

요구사항:
- 화재감지기 연기 감지 → 15초 취소 대기 → 119 자동 신고 흐름
- 응급호출기 버튼 → 동일 취소 로직 → 119 자동 신고 흐름
- 취소 신호 수신 시 자동 철회
- 규칙은 선언적 구조(dict/config)로 관리
- 입력: STEP 0에서 정의한 센서 Raw 데이터 모델
- 출력: STEP 0에서 정의한 판단 결과 모델
- 다른 Edge AI 모듈(패턴매칭, 경량예측)과 독립적으로 동작
- 판단 로그를 남겨서 Core AI 학습 데이터로 활용 가능하도록

먼저 클래스 구조와 규칙 설정 방식의 설계안을 보여줘.
내가 확인하면 구현해.
```

**검증 포인트**:
- 규칙 추가/변경 시 코드 수정 없이 config만으로 가능한지
- 센서 이벤트 수신 → 판단 → 출력까지의 흐름이 명확한지
- 취소 로직의 타이밍 처리가 정확한지
- 출력이 STEP 0 스키마와 호환되는지

### STEP 2: 비지도학습 기반 패턴 매칭

```
[주문 예시]

PROJECT_GUIDELINES.md와 첨부한 schemas.py를 참고해서 아래 작업을 수행해줘.

작업: Edge AI - 비지도학습 기반 패턴 매칭 파이프라인 구현

요구사항:
- 파이프라인: 센서 raw → Kalman Filter → EWMA → Isolation Forest → 이상 점수
- 각 알고리즘은 독립 모듈로 구현 (파이프라인 조합 변경 가능)
- 복합 센서 교차 검증 로직 (열사병/낙상/저체온 시나리오)
- 외부 Context(기상특보) 수신 시 임계값 동적 조정
- 개인화 DB 기반 대상자별 임계값 보정
- 1~5분 주기 판단 사이클
- 라벨 없이 즉시 동작 가능

입력: STEP 0의 센서 Raw 데이터 모델 (복수 센서)
출력: STEP 0의 Edge AI 전처리 결과 모델 (상황등급 포함)

먼저 파이프라인 클래스 구조와 각 알고리즘의 인터페이스 설계안을 보여줘.
내가 확인하면 구현해.
```

**검증 포인트**:
- Kalman Filter → EWMA → IF 순서대로 데이터가 흐르는지
- 각 알고리즘을 개별 교체할 수 있는 구조인지
- 복합 시나리오(열사병 등) 판단 로직이 제안서 내용과 일치하는지
- 임계값 동적 조정이 실제 동작하는지
- 출력이 STEP 0 스키마와 호환되는지

### STEP 3: 경량 예측 파이프라인

```
[주문 예시]

PROJECT_GUIDELINES.md와 첨부한 schemas.py, edge_pattern_matching.py를 참고해줘.

작업: Edge AI - 경량 예측 파이프라인 구현

요구사항:
- FITS 기반 초경량 시계열 예측 (호환성 문제 시 대안 제안)
- 7일 데이터 기반 1차 이상 등급 산출
- Haversine 공식으로 GPS 기반 미귀가 판단
- 이상 점수·추세 축약 데이터 산출
- 게이트웨이 리소스 제약 고려한 경량 구현

입력: STEP 2의 전처리 결과 + 센서 누적 이력 + 모바일앱 데이터
출력: STEP 0의 Edge → Core 전달용 축약 데이터 모델

먼저 설계안을 보여줘.
```

**검증 포인트**:
- 게이트웨이에서 실행 가능한 수준의 경량성인지
- 축약 데이터가 Core AI 입력 스키마와 정확히 호환되는지
- 7일 윈도우 데이터 관리 방식이 현실적인지
- Haversine 거리 계산이 정확한지

### STEP 4: Core AI 학습 시스템

```
[주문 예시]

PROJECT_GUIDELINES.md와 첨부한 schemas.py를 참고해줘.

작업: Core AI - 학습 시스템 구현

요구사항:
- 전처리 학습 데이터 생성 파이프라인
- 1단계: 비지도학습 기반 초기 모델 (공개 데이터 기반 임계값)
- 2단계: 라벨 수집 구조 (요원 피드백 → 라벨 DB)
- 3단계: 지도학습 전환 (비지도 → 지도 자연스러운 전환)
- 모델 버전 관리
- 학습 완료 모델 → 추론 서버 및 게이트웨이 배포 구조

입력: ClickHouse의 누적 데이터 + Edge 축약 데이터 + 라벨 DB
출력: 학습된 추론 모델 (버전 관리)

먼저 학습 파이프라인 아키텍처와 모델 전환 전략 설계안을 보여줘.
```

**검증 포인트**:
- 비지도 → 지도 전환이 기존 모델을 깨뜨리지 않는지
- 라벨 수집 파이프라인이 운영 중 추가 가능한지
- 모델 버전 롤백이 가능한지
- 재학습 트리거 조건이 명확한지

## 각 STEP의 진행 방식 (3단계)

모든 STEP은 아래 순서를 따른다:

### 1단계: 설계 검토 (코드 작성 전)

클로드에게 먼저 설계안만 요청한다.
확인할 것:
- 클래스/모듈 구조도
- 입출력 데이터 흐름
- 이전 모듈과의 인터페이스 호환성
- 제안서 내용과의 일치 여부

문제가 있으면 이 단계에서 수정 요청한다.

### 2단계: 구현

설계 확인 후 "구현해줘"라고 요청한다.
확인할 것:
- 스키마 타입 일치
- 불필요한 주석 없는지
- 코드 길이가 과하지 않은지
- 이전 모듈의 출력을 입력으로 받을 수 있는지

### 3단계: 테스트

구현 완료 후 테스트 코드를 요청한다:
```
이 모듈의 테스트 코드를 작성해줘.
- 정상 케이스
- 경계값 케이스
- 이전 모듈 출력을 입력으로 사용하는 통합 테스트
```

테스트 통과 확인 후 다음 STEP으로 진행한다.

## 주의사항

### 대화 분리
- 하나의 대화에서 2개 이상의 STEP을 진행하지 않는다.
- 대화가 길어지면 새 대화를 열고 지침서 + 이전 산출물을 다시 제공한다.

### 산출물 관리
- 각 STEP의 최종 코드를 파일로 저장하고 다음 STEP에 첨부한다.
- 스키마 변경이 생기면 이전 모듈도 함께 업데이트한다.

### 설계 변경 시
- 제안서 알고리즘(FITS, TimesFM 등)이 실제 구현에서 문제가 있으면 대안을 제안받는다.
- 대안 채택 시 지침서(PROJECT_GUIDELINES.md)도 업데이트한다.

### 검증 체크리스트 (매 STEP 완료 시)
- [ ] STEP 0 스키마와 입출력이 호환되는가
- [ ] 이전 모듈의 출력을 입력으로 사용할 수 있는가
- [ ] 다음 모듈이 이 출력을 받을 수 있는가
- [ ] 제안서의 해당 섹션 내용과 일치하는가
- [ ] 테스트가 통과하는가
- [ ] 불필요한 주석이 없는가
- [ ] 확장/교체가 용이한 구조인가
