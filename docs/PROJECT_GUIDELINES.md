# 댁내 응급안전안심서비스 AI 플랫폼 구현 지침

## 프로젝트 개요

보건복지부 응급안전안심서비스의 AI 플랫폼 기술 요소를 구현한다.
Edge AI(게이트웨이)와 Core AI(중앙 서버)의 2계층 구조로, 센서 데이터 기반 이상징후 탐지·예측·대응 파이프라인을 구축한다.

대상자 규모: 9.4만 명 / 게이트웨이 9.4만 대 / 월간 트래픽 약 6.89TB

---

## 1. 아키텍처 원칙

### 1.1 계층 구조

```
[센서 4종 + 모바일앱] → [게이트웨이(Edge AI)] → [Kafka 수집서버] → [ClickHouse + Qdrant] → [Core AI]
                                                                                                ↓
                                                                              [디지털돌봄시스템 / 관리요원앱]
```

### 1.2 판단 우선순위

1. **센서 이벤트(최우선)**: 화재·응급호출 → Expert System → 119 자동 신고. AI 판단과 무관하게 독립 실행.
2. **Edge AI 복합 판단**: 1~5분 주기. 복수 센서 교차 검증 기반 이상 감지.
3. **Core AI 정밀 추론**: Edge에서 위험 등급 상향 시 해당 대상자에 대해 트리거.

동일 대상자에 센서 이벤트와 AI 경보 동시 발생 시, 센서 이벤트가 이미 119를 트리거했으면 AI 경보는 참고 정보로 처리하여 중복 출동을 방지한다.

### 1.3 설계 제약

- Core AI는 상시 구동이 아니라 이벤트 트리거 기반으로 동작한다.
- 센서 전송 주기가 5초~4시간으로 다양하므로 모든 데이터가 실시간 도달하지 않는다.
- 데이터/알고리즘은 운영 중 변경될 수 있으므로 모듈 교체가 용이한 구조로 설계한다.

## 2. 데이터 명세

### 2.1 센서 데이터 (Zigbee → 게이트웨이)

게이트웨이로의 센서 연결은 Zigbee 프로토콜을 사용한다. 게이트웨이에서 서버로의 전송은 JSON 포맷이다.

| 장비 | 전송 주기 | 주요 필드 |
|------|----------|----------|
| 온도센서 | 10분 | sensor_id, type:"temp", value, unit:"C", ts, device_id, seq |
| 습도센서 | 10분 | sensor_id, type:"humi", value, unit:"%", ts, device_id, seq |
| 조도센서 | - | sensor_id, type:"lux", value, unit:"lx", ts, device_id, seq |
| 게이트웨이 활동량센서 | 1분 | sensor_id, period_start, period_end, value, count, max, min, device_id, seq, status |
| 활동감지기(PIR) | 1분 | sensor_id, period_start, period_end, value, count, max, min, device_id, seq, status |
| 화재감지기 | 이벤트 | sensor_id, state:("smoke"/"normal"), ts, device_id, seq, status |
| 응급호출기 | 이벤트 | sensor_id, state:("red"/"normal"), ts, device_id, seq, status |
| 출입감지기 | 이벤트 | sensor_id, state:("open"/"normal"), direction:("in"/"out"/"-"), ts, device_id, seq, status |

### 2.2 모바일 활동감지앱 데이터

| 장비 | 주요 필드 |
|------|----------|
| 위험도 판단 결과 | subject_id, risk_level, fall, no_return, usage_anomaly, long_inactivity, ts, device_id |
| GPS 정보 | subject_id, lat, lon, ts, device_id |

### 2.3 데이터 사이즈 기준

- 센싱 값 1개: 20~30B (헤더 포함 약 81B)
- 대상자 1인당: 약 70MB/월 (모바일 포함 시 71MB/월)
- 전체 9.4만 대: 약 6.89TB/월 (약 230GB/일)

### 2.4 공통 데이터 인터페이스

모든 모듈 간 데이터 교환은 통일된 스키마를 사용한다. 각 모듈 구현 시 아래 원칙을 따른다:

- 입출력 데이터 모델을 Pydantic 또는 dataclass로 정의한다.
- 센서 raw → 전처리 → 피처 → 판단결과의 단계별 스키마를 명확히 분리한다.
- 타임스탬프는 Unix epoch(초 단위)으로 통일한다.

## 3. Edge AI 구현

게이트웨이 내에서 동작하는 경량 AI 파이프라인. 3개 모듈로 구성한다.


### 3.0 Edge AI 개발·배포 전략

- 알고리즘 설계·검증·학습은 Python(Core AI 서버)에서 수행한다.
- 게이트웨이 배포 코드는 C/C++ (또는 Lua)로 경량 구현한다.
- 게이트웨이에서는 추론만 수행하며, 학습은 하지 않는다.
- Core AI에서 학습된 모델 파라미터(트리 구조, 가중치 등)를 직렬화하여 게이트웨이에 배포한다.
- 구현 순서: Python 프로토타입 → 검증 → C/C++ 포팅

### 3.1 Expert System (이벤트 감지)

**목적**: 화재·응급호출 등 명확한 위험 상황의 즉각 판단 및 119 자동 신고.

**구현 요건**:
- 사전 정의된 규칙과 조건 분기 기반의 규칙 엔진
- 화재감지기 연기 감지 → 취소 멘트 안내(15초간 2회 송출) → 취소 입력 없으면 119 자동 신고
- 응급호출기 버튼 → 동일 취소 로직 → 119 자동 신고
- 취소 신호 수신 시 신고 자동 철회 (오작동 방지)
- 센서 이벤트는 AI 판단과 독립적으로 최우선 실행

**입력**: 화재감지기(열/연기), 응급호출기, 게이트웨이 119호출기 이벤트
**출력**: 119 자동 신고 트리거, 거점/응급 관리요원 앱 알림

**설계 지침**:
- 규칙은 선언적 구조(dict/config)로 관리하여 추가·변경이 용이하도록 한다.
- 판단 로직은 센서 이벤트 수신 즉시 실행되며, 다른 모듈의 판단을 기다리지 않는다.
- 판단 결과와 이벤트 로그를 구조화하여 Core AI 학습 데이터로 활용할 수 있도록 한다.

### 3.2 비지도학습 기반 패턴 매칭

**목적**: 복수 센서의 교차 검증을 통한 복합 이상 상황 감지.

**구현 알고리즘**:

1. **Kalman Filter**: 센서 수신값의 노이즈를 직전 관측값 기반으로 실시간 보정. 측정값과 보정값의 가중치를 조절 가능.
2. **EWMA (Exponentially Weighted Moving Average)**: 칼만 필터 출력을 지수 가중 이동평균으로 정제. 최근 값일수록 높은 가중치.
3. **Isolation Forest**: 정제된 패턴에서 이상치 우선 인식. 고차원 복합 패턴 인식 가능. 변수 조정으로 개인화 적용.

**처리 파이프라인**: `센서 raw → Kalman Filter → EWMA → Isolation Forest → 이상 점수 산출`

**복합 센서 교차 검증 시나리오**:
- 열사병: 폭염 시 임계값 하향 → 고온 + 활동미감지 ≥30분
- 낙상: 화장실 재실 + 타 공간 활동감지기/센서 미반응 ≥30분
- 저체온: 거동불편 시 임계값 조절 → 실내 ≤15°C + 활동 급감
  - 참고 기준: WHO Housing and Health Guidelines (2018) - 실내 최저 권장온도 18°C

**파라미터 동적 조정**:
- 외부 Context(기상특보, 재난문자) 수신 시 임계값을 동적으로 변경
- 개인화 DB(거동불편, 거주지 등) 기반 대상자별 임계값 보정

**설계 지침**:
- 1~5분 주기로 판단 사이클을 실행한다.
- 각 알고리즘은 독립 모듈로 구현하여 파이프라인 조합이 가능하도록 한다.
- 판단 결과는 상황등급(관심/주의/위험)으로 분류하여 차등 전송한다.
- 라벨 없이 즉시 동작 가능해야 한다(초기 운영 시 라벨 데이터 부재).

### 3.3 경량 예측 파이프라인

**목적**: 이상 점수·추세 축약 데이터를 산출하여 Core AI로 전달.

**구현 알고리즘**:

1. **FITS (Frequency Interpolation Time Series Analysis Baseline)**: 약 1만 개 매개변수의 초경량 모델. 1~2분 단위 구간 설정 가능. 분 단위 예측·개인화에 최적.
2. **Isolation Forest**: 경량 예측 파이프라인에서도 이상 점수 산출에 활용.

**입력**: 센서 누적 이력(활동·온습도·조도·출입), 모바일 활동감지 앱, 개인화 DB, 외부 Context
**출력**: 이상 점수, 추세 축약 데이터, 이상징후 등급 → Core AI 전달 및 요원 출동 트리거

**거주지 복귀 불가 예측**:
- Haversine 공식으로 GPS 좌표 간 실제 지표면 거리 계산
- 기존 외출 패턴과 다른 상황 발생 시 미복귀 응급 상황 추론

**설계 지침**:
- Edge AI는 7일 데이터 기반으로 1차 이상 등급을 산출한다.
- 게이트웨이 리소스 제약을 고려하여 경량 모델만 사용한다.
- 축약 데이터 포맷을 Core AI 입력 스키마와 호환되도록 설계한다.
- 제안서에 명시된 알고리즘(FITS, IF)은 호환성 문제 시 동급 경량 대안으로 교체 가능하다.

## 4. Core AI 구현

중앙 서버에서 동작하는 학습·추론 시스템. 학습을 먼저 수행한 뒤 추론 모델을 배포하는 구조이다.

### 4.1 데이터 흐름 (서버 측)

```
[Kafka 수집서버] → [ClickHouse 데이터레이크] → [전처리] → [Core AI 학습/추론 서버]
                                                    ↓
                                              [벡터 DB (Qdrant)]
```

**데이터레이크 구성 (ClickHouse)**:
- 디지털돌봄시스템 정보
- 센싱 데이터 및 현장 패턴 정보
- 대상자 기초자료 / 외부 컨텍스트 데이터
- STT 데이터 (케어콜·응급요원 리포트)

**벡터 DB (Qdrant)**:
- HNSW 알고리즘 기반 고성능 벡터 데이터베이스
- 센싱 패턴, 텍스트를 벡터로 임베딩하여 보관
- Core AI에서 유사도 검색에 즉시 활용

### 4.2 학습 시스템

**목적**: 누적 데이터 기반으로 추론 모델을 학습하고, 학습 완료된 모델을 배포한다.

**학습 전략 (3단계)**:

| 단계 | 시기 | 전략 |
|------|------|------|
| 1단계 | 착수~8월말 | 개인 패턴 학습 후 Expert System 판단. 라벨 없이 비지도학습으로 즉시 동작. 공개 데이터(AI데이터허브 '치매 예방을 위한 라이프로그' 148명) 기반 초기 임계값 설정. |
| 2단계 | 9월~11월말 | 응급관리요원 앱 연동 라벨 수집 시작. 응급 처리 결과 → 중계서버 저장. 응급상황 시점 전후 시계열 데이터를 이상 징후 판단 패턴으로 정의. ClickHouse에 이력 누적. |
| 3단계 | '27년 1월~ | 지도학습 전환. 다수 대상자의 확정 응급 이력을 라벨로 재학습. 학습 결과 기반 개인별 판단 임계값을 게이트웨이에 자동 반영. |

**라벨 수집 파이프라인**:
```
AI 이상 감지 경보 → 응급안전요원 현장 출동 → 사건 처리 → 앱에서 결과 입력 → 디지털돌봄+중계서버 동시 저장 → 라벨DB 생성 → 지도학습 진행
```

**설계 지침**:
- 비지도학습 → 지도학습으로의 자연스러운 전환 구조를 설계한다.
- 학습 완료된 모델은 버전 관리하고, 추론 서버 및 게이트웨이에 배포한다.
- 재학습 주기와 트리거 조건을 설정 가능하도록 한다.

### 4.3 추론 시스템

**목적**: Edge에서 위험 등급 상향 시 해당 대상자에 대해 정밀 추론을 수행한다.

**구현 모델**:

1. **Sentence Embedding 기반 응급 사례 예측**
   - 수집 데이터를 Sentence Embedding으로 변환 → Qdrant 벡터 DB 저장
   - Edge AI에서 위험 등급·패턴 데이터 수신 시, 기존 사례와 코사인 유사도 비교로 위험도 예측
   - 확정 응급 사례만으로 벡터 DB 구축 (예: "배가 아파요"와 "복통이 심해요" 매칭)

2. **Sequential Transformer 기반 이상 패턴 탐지**
   - 시계열 데이터의 연속 흐름에서 이상 패턴을 탐지
   - 개인화 프로파일을 함께 입력하여 개인별 습관·패턴 반영 정밀 예측
   - 최대 30일간 센서 누적 패턴을 학습하여 24시간 내 응급 발생 확률 예측
   - **Anomaly Transformer**: 시간대별 센싱 패턴 기반 이상치 탐지 특화
   - **iTransformer**: 센서 간 상호 관계 분석, 다중 센서 복합 패턴 이상치 탐지 최적화

3. **TimesFM (시계열 Foundation Model)**
   - Google 개발 시계열 Foundation Model
   - 장기간 관측이 필요한 응급 상황에 적합
   - 모델 크기가 작고 빠름
   - LoRA 기반 Fine Tuning으로 응급 상황별 프로파일링

**추론 흐름**:
```
Edge AI 축약 데이터 + 개인화 프로파일 → Core AI 추론 → 응급 상황 위험도 판별 결과
                                                          ↓
                                             예측 등급(관심/주의/위험) 산출
                                                          ↓
                                             "위험" → 응급관리요원 즉시 알림
                                             "추가 분석 필요" → Core AI 최종 예측
```

**대상자별 임계값 조정**: 예측 등급 범위를 컨피던스 점수 기반으로 대상자 특성에 맞게 보정한다.

**설계 지침**:
- 추론은 상시 구동이 아닌 이벤트 트리거 방식이다.
- 각 모델(Sentence Embedding, Transformer, TimesFM)은 독립 모듈로 구현한다.
- 추론 결과는 관제 시스템, 응급관리요원, 보호자 알림 케어 시스템에 전달한다.
- 제안서에 명시된 모델은 호환성 문제 시 동급 대안으로 교체 가능하다.

### 4.4 STT 데이터 활용 체계

**목적**: 케어콜·응급요원 현장 리포트의 텍스트를 벡터화하여 유사 응급 사례 매칭.

**3단계 구축**:
1. 확정 응급 사례 DB 구축 → Sentence Embedding → 코사인 유사도 기반 매칭 서비스 개시
2. 신규 STT 수신 시 동일 임베딩 모델로 벡터화 → 확정 사례 DB와 비교 → 예측. 현장 요원 피드백 → 라벨링 반영.
3. 축적된 검증 사례 DB와 대상자 정보로 유사도 검색 임계값 보정 → 정밀도 지속 향상.

## 7. 구현 순서 가이드

각 모듈을 아래 순서로 구현한다. 앞 단계의 출력 스키마가 뒷 단계의 입력이 되므로, 데이터 인터페이스를 먼저 확정한다.

### Phase 0: 데이터 스키마 및 공통 인프라
1. 센서 데이터 모델 정의 (Pydantic/dataclass)
2. Edge → Core 전달용 축약 데이터 스키마 정의
3. 판단 결과(상황등급) 스키마 정의
4. 설정/임계값 관리 구조 설계

### Phase 1: Edge AI
0. Python 프로토타입으로 알고리즘 검증 후 C/C++ 포팅
1. Expert System 규칙 엔진
2. Kalman Filter → EWMA 전처리 파이프라인
3. Isolation Forest 기반 이상 탐지
4. FITS 기반 경량 예측
5. 상황등급 판정 및 차등 전송 로직
6. 외부 Context 연동 (기상특보, 재난문자) 임계값 동적 조정

### Phase 2: 데이터 파이프라인
1. Kafka 기반 수집 서버
2. ClickHouse 적재 및 전처리
3. Qdrant 벡터 DB 구축
4. STT 서버 연동

### Phase 3: Core AI 학습
1. 전처리 학습 데이터 생성 파이프라인
2. 비지도학습 기반 초기 모델 학습
3. 라벨 수집 및 지도학습 전환 구조
4. 모델 버전 관리 및 배포 파이프라인

### Phase 4: Core AI 추론
1. Sentence Embedding + 벡터 DB 유사도 검색
2. Sequential Transformer 기반 시계열 추론
3. TimesFM LoRA Fine Tuning
4. 추론 결과 → 관제 시스템/요원 앱 알림 연동

### Phase 5: 피드백 루프
1. 요원 현장 결과 → 라벨 DB 축적
2. 재학습 트리거 및 자동 재학습
3. 게이트웨이 모델/임계값 재배포

## 8. 코드 컨벤션

- 테스트 가능한 구조로 설계한다.
- 확장 가능성을 고려하여 인터페이스/추상 클래스를 활용한다.
